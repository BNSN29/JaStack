What is this repo?

An all-in-one research-grade framework for developing, simulating, and deploying autonomous multi-drone systems. It bridges the gap between algorithm prototyping and real hardware in one unified, Dockerized stack.

🌐 Simulate

Dockerized Gazebo Sim with 5 photorealistic worlds, multiple vehicle models, YOLO + LiDAR perception. Runs faster-than-real-time (e.g. RTF=3.0) and exposes a Gymnasium RL interface.
🚀 Deploy

Targets NVIDIA Jetson Orin NX with JetPack + DeepStream. TensorRT-accelerated YOLO, Livox LiDAR, GStreamer video pipeline. One ./deploy_run.sh command.
🎯 Who is this for?

Researchers and engineers who need to go from "I have a drone autonomy idea" to "I tested it in sim AND on a real quadrotor" without gluing together 10 separate projects. The author (Jacopo Panerati, now at NRC Canada) also wrote gym-pybullet-drones and published the autonomous drone racing dataset — this is the real-hardware successor.

System Architecture

How the three containers talk to each other — and how real hardware fits in.

Data flow at a glance
🌐 Gazebo
simulation-container
PX4/ArduPilot SITL
→
✈️ Aircraft
aircraft-container ×N
YOLO · KISS-ICP · Control
⇄
📡 Ground
ground-container
QGC · Zenoh · Tracking
  • Gazebo renders the 3D world and runs SITL flight controllers. It sends camera/LiDAR streams over SIM_SUBNET (a Docker bridge network).
  • Each aircraft container runs one complete perception + control stack per drone. Multiple containers = multi-drone swarm.
  • Zenoh is the inter-vehicle and aircraft↔ground bridge — it routes ROS2 topics over TCP across the AIR_SUBNET, enabling real swarm communication patterns even in sim.
  • mavlink-router on the ground side routes MAVLink telemetry to QGroundControl.

ArduPilot uses GUIDED mode; MAVROS translates between MAVLink and ROS2.

Key Workflows

The most common things you'll actually do with this repo.

🏗 1. Build the simulation (first time) ▶
Requires: Ubuntu 24.04, nvidia-driver-580, Docker Engine v29, nvidia-container-toolkit. Run ./tests/check_requirements.sh first.
sudo apt update && sudo apt install -y git xterm xfonts-base wget unzip
git clone https://github.com/JacopoPan/aerial-autonomy-stack.git
cd aerial-autonomy-stack/tools_and_docs/
./sim_build.sh    # ~45 min on first run; Docker layer caching makes re-runs fast
Or pull pre-built images from GitHub Container Registry (rebuilt every Friday night from main):
docker pull ghcr.io/jacopopan/aircraft-image:latest
✈️ 2. Run a multi-drone simulation ▶ 
# Terminal 1 — start the world
cd aerial-autonomy-stack/tools_and_docs/
AUTOPILOT=px4 NUM_QUADS=2 NUM_VTOLS=1 WORLD=swiss_town RTF=3.0 ./sim_run.sh

# Terminal 2 — fly all drones using the mission orchestrator
for ID in {1..3}; do
  docker exec -d aircraft-container-inst0_$ID bash -c "source /opt/ros/humble/setup.bash &&
    source /aas/aircraft_ws/install/setup.bash &&
    ros2 run mission mission --conops yalla.yaml --ros-args -r __ns:=/Drone$ID -p use_sim_time:=true"
done
VariableOptionsWhat it controls
AUTOPILOTpx4, ardupilotWhich flight controller stack runs
NUM_QUADS0, 1, 2, …Number of quadrotor instances
NUM_VTOLS0, 1, 2, …Number of VTOL (fixed-wing transition) instances
WORLD5 optionsGazebo world loaded
RTF1.0, 2.0, … / 0.0Real-time factor (0.0 = as fast as possible)

DEVtrue, falseMount source folders as volumes for live editing
🤖 3. Control a drone from ROS2 CLI ▶ 
# Set your drone ID
DRONE_ID=1

# Takeoff to 40m
cancellable_action "ros2 action send_goal /Drone${DRONE_ID}/takeoff_action \
  autopilot_interface_msgs/action/Takeoff \
  '{takeoff_altitude: 40.0}'"

# Orbit around a GPS point
cancellable_action "ros2 action send_goal /Drone${DRONE_ID}/orbit_action \
  autopilot_interface_msgs/action/Orbit \
  '{east: 500.0, north: 0.0, altitude: 150.0, radius: 200.0}'"

# Offboard (low-level rate control for 5 sec)
cancellable_action "ros2 action send_goal /Drone${DRONE_ID}/offboard_action \
  autopilot_interface_msgs/action/Offboard \
  '{offboard_setpoint_type: 1, max_duration_sec: 5.0}'"

# Land
cancellable_action "ros2 action send_goal /Drone${DRONE_ID}/land_action \
  autopilot_interface_msgs/action/Land '{landing_altitude: 60.0}'"

# Gimbal control
ros2 topic pub -1 /gimbal_pitch_cmd std_msgs/msg/Float64 "{data: 1.57}"
The cancellable_action helper lets you Ctrl+C to abort mid-action — the drone will hover and wait for the next command.
🏋️ 4. Use as a Gymnasium RL environment ▶ 
# Install
conda activate aas
cd aerial-autonomy-stack/aas-gym/
pip3 install -e .

# Run examples
python3 tools_and_docs/gym_run.py --mode step          # 1 Hz manual stepping
python3 tools_and_docs/gym_run.py --mode speedup       # 50 Hz speed test
python3 tools_and_docs/gym_run.py --mode vectorenv-speedup  # parallel envs

The aas_env.py wraps the full simulation as a standard Gymnasium environment. Your RL agent calls env.step(action) and the sim runs at the configured RTF. Vectorised envs are supported for parallelized rollouts.

🔧 6. Develop live inside containers ▶ 
# Mount source as volumes — edit on host, build in container
DEV=true ./sim_run.sh

# Inside the QUAD Xterm:
cd /aas/aircraft_ws/
colcon build --symlink-install

# Start/stop the sim without rebuilding the image

In DEV mode, aircraft_resources/, aircraft_ws/src/, etc. are bind-mounted. Changes you make on the host are immediately visible inside the container — you only need to colcon build, not rebuild the Docker image.

Key Modules Deep-Dive

The packages you'll most likely read, modify, or extend.

🎮 autopilot_interface — the ROS2 action server
aircraft/aircraft_ws/src/autopilot_interface/

This is the abstraction layer between your high-level mission logic and the autopilot. It hides whether you're using PX4 or ArduPilot.

Action/ServiceTypeDescription
/DroneN/takeoff_actionActionArm + take off to altitude. For VTOLs, handles transition heading and loiter point.
/DroneN/land_actionActionReturn and land. VTOLs transition back to multirotor mode.
/DroneN/orbit_actionActionCircle a GPS coordinate at given radius/altitude.
/DroneN/offboard_actionActionHand control to offboard_control node for setpoint_type duration.
/DroneN/set_repositionServiceFly to an NED position (quads only).
/DroneN/set_speedServiceSet cruise speed (limited by autopilot params).
The offboard_setpoint_type values: 0=attitude, 1=rates, 2=trajectory (PX4); 3=velocity, 4=acceleration (ArduPilot)
🗺 mission — YAML-driven flight orchestration
aircraft/aircraft_ws/src/mission/

Instead of writing C++ to sequence actions, you define a CONOPS (concept of operations) in YAML. The mission node reads it and calls the action servers in order.

# Example: aircraft/aircraft_resources/missions/test_mission.yaml
# (Create your own missions by copying this file)
ros2 run mission mission --conops your_mission.yaml \
  --ros-args -r __ns:=/Drone1 -p use_sim_time:=true

For swarms: launch the mission node for each drone in parallel with different __ns values.

👁 yolo_py — perception pipeline
aircraft/aircraft_ws/src/yolo_py/

In simulation: GStreamer pulls the camera stream from Gazebo via gz_gst_bridge. On Jetson hardware: GStreamer reads from the IMX219 camera via DeepStream.

YOLO runs via ONNX Runtime with GPU acceleration (TensorRT FP16 cache built on first run, ~10 min). Publishes bounding boxes on /detections, consumed by offboard_control for visual servoing.

To change YOLO model or sensor parameters, edit simulation/simulation_resources/aircraft_models/sensor_config.yaml and re-run ./sim_build.sh.
🔗 state_sharing + Zenoh — swarm awareness
aircraft/aircraft_ws/src/state_sharing/

Each drone publishes its own state (position, velocity, heading) to /state_sharing_drone_N. The Zenoh bridge forwards this over TCP across the AIR_SUBNET, so every other drone (and the ground station) can subscribe to /state_sharing_drone_M and know where its neighbors are.

This is how the stack achieves decentralized swarm coordination without a central server — every drone knows the state of every other drone in real time.

🏋️ aas_env.py — Gymnasium interface
aas-gym/src/aas_gym/aas_env.py

Wraps the entire simulation stack as a standard gymnasium.Env. Your RL agent interacts with it via the standard reset() / step(action) / render() interface. The simulation can run at any RTF, so training is much faster than wall-clock time.

Vectorized via standard Gymnasium VectorEnv — you can run N parallel simulation instances (each with a different INSTANCE ID) and collect rollouts in parallel.

🔒 Why these exact versions? (dependency chain)

The version pinning isn't arbitrary — it's a chain of hard constraints:

  • Jetson Orin only supports JetPack ≤ 6 → L4T 36 → Ubuntu 22 → Python 3.10
  • Python 3.10 max ONNX Runtime GPU wheel is 1.23.2 (1.24+ needs Python 3.11+)
  • ONNX Runtime 1.23.2 only supports CUDA 12 (CUDA 13 added in 1.24.1) → CUDA 12.9.2
  • Ubuntu 22 ships GStreamer 1.20 → nvh264enc presets deprecated beyond nvidia-driver-595 → must stay on nvidia-driver-580
  • This chain is why amd64 also uses Ubuntu 22 as the Docker base, even though the host is Ubuntu 24
Upgrading any one of these may break the chain. Check the "Dependencies management" section of the README before bumping versions.

📊 48 commits behind: should you care?

For most use-cases, being 48 commits behind is fine — this is a research tooling repo, not a rapidly changing library you depend on via API. The codebase is stable. However there are specific scenarios where catching up matters:

ScenarioShould you sync?
You're using the pre-built ghcr.io imagesYes — images are rebuilt from main weekly
You've made local changes to aircraft_ws/srcMaybe — check if upstream changed the same files
You only run sim with your own missionsProbably not — your YAML missions are unaffected
Fixing a bug that might be fixed upstreamYes — check the issues/commits first
🔄 How to sync your fork with upstream
# One-time: add upstream remote
git remote add upstream https://github.com/JacopoPan/aerial-autonomy-stack.git

# Fetch latest upstream commits
git fetch upstream

# See what changed (without applying)
git log HEAD..upstream/main --oneline

# Option A: fast-forward if you have NO local commits on main
git checkout main
git merge upstream/main

# Option B: rebase your local commits on top of upstream
git rebase upstream/main

# Option C: cherry-pick only specific upstream commits
git cherry-pick <commit-sha>
If you've been working in a branch (recommended!), Option B is cleanest — it replays your changes on top of the updated main.
🛡 Best practices for customizing this repo
  • Never edit main directly. Keep main as a clean mirror of upstream. Do all your work in feature branches.
  • Your mission files live in aircraft/aircraft_resources/missions/ — these are safe to commit to your fork and won't conflict with upstream changes.
  • Custom sensor config in simulation/simulation_resources/aircraft_models/sensor_config.yaml — version-control this separately or in a branch.
  • For new ROS2 nodes, add them to aircraft_ws/src/ as new packages (don't modify existing packages) — this avoids merge conflicts.
  • Check tools_and_docs/docs/REQUIREMENTS_UBUNTU.md after syncing — host requirements sometimes change between releases.
